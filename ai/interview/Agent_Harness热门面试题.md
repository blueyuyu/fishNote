## Q3：Agent、普通 LLM 对话、Chain、Workflow 和 Agent Harness 分别是什么？

**回答主线：**

- 普通 LLM 对话是输入文本、模型生成文本，程序主要负责请求和展示。
- Chain 是开发者预先写好的顺序调用，例如“检索—拼接—生成”，路径基本固定。
- Workflow 是确定性业务流程，可以有条件分支、并行和审批，但步骤仍主要由程序决定。
- Agent 允许模型根据当前状态选择下一步行动、工具和是否继续。
- Agent Harness 是包住模型的工程运行时与治理层，负责循环、状态、上下文、工具注册、参数校验、权限、预算、超时、恢复、审计、评测和降级。

可以用一句话概括：**模型负责提出下一步，Harness 决定这一步是否允许、怎样执行、结果怎样进入状态，以及什么时候必须停止。**

在 DevPilot 中，模型只是决策组件；LangGraph、业务状态表、审批策略、本地执行器、工作副本、上下文预算和审计共同组成 Harness。直接调用大模型 API 不具备这些运行保障。

## Q4：什么时候不应该使用 Agent？为什么有些场景固定工作流更稳定？

**参考回答：**

当任务步骤稳定、规则明确、错误成本高、输出可以由程序确定时，应优先使用普通代码或有向无环图工作流。例如权限判断、金额计算、单位转换、数据库事务和固定审批流不应交给模型自由决策。

只有任务存在明显的不确定性，例如需要从大量资料中寻找信息、根据中间结果动态选择工具、无法提前穷举路径，Agent 才能带来价值。即使使用 Agent，也应该把确定性部分留在程序里。

DevPilot 就是混合方案：模型决定需要查哪些代码、是否建议修改；目录边界、参数校验、审批、真实命令执行和最终写回由确定性系统控制。这样避免把“智能”误解为“所有事情都交给模型”。

## Q5：如果从零搭建一个 Agent 平台，你会如何分层？

**建议在白板上画七层：**

```text
交互层：Web / Electron、流式消息、进度、审批、Diff
接入层：身份认证、租户、配额、幂等请求、API
编排层：Agent Loop、LangGraph、状态机、检查点、人工中断
智能层：模型网关、结构化输出、上下文组装、多模型路由
工具层：工具注册、MCP、参数校验、执行器、结果适配
数据层：PostgreSQL、Redis、对象存储、ES、Milvus
治理层：权限、审计、评测、Trace、成本、告警、降级
```

平台设计时先定义状态和失败语义，再选框架。必须回答：任务存在哪里、谁拥有执行权、工具执行一半崩溃怎么办、用户撤权后旧任务能否继续、模型升级怎样回归、无模型时能否降级。框架只是实现手段。

**项目映射：**DevPilot 的 Electron/FastAPI/本地执行器对应交互、平台和执行边界；LangGraph 与 PostgreSQL 对应可恢复编排；Veloxis 的 ES/Milvus/图谱对应知识层；LangFuse、审批与审计对应治理层。

## Q6：如何判断一个新 Agent 框架值不值得引入？LangGraph 和自研循环怎么选择？

**参考回答：**

我会从六个维度评估：是否解决当前痛点、状态模型是否清晰、持久化与恢复能力、人工中断和工具生态、可观测性与测试能力、迁移和锁定成本。先用一条真实链路做小规模验证，再比较现有基线，不因为社区热度直接替换。

简单的单轮抽取或固定工具流程，自研函数和状态机更直观；需要条件分支、循环、人工中断、检查点和可视化状态时，LangGraph 更合适。DevPilot 早期用显式 `asyncio` 循环验证执行语义，当前使用 LangGraph 组织流程，同时保留业务表和执行账本。原因是框架解决“流程从哪里继续”，但不能替代业务事实、权限和副作用记录。

推动新技术时，我会提供最小可运行样例、迁移边界、回滚方案、性能与质量对比，并让团队共同评审。宁德时代的组件知识库、Figma-to-UI、OpenSpec 和 TDD 都采用了类似的渐进落地方式。

# 第二组：Agent Loop、LangGraph 与任务恢复

## Q7：ReAct 和 Plan-and-Execute 有什么区别？你如何选择？

**参考回答：**

ReAct 是“观察当前状态—思考—执行一个动作—接收结果—继续判断”的短反馈循环，适合路径不明确、需要边查边决定的任务。优点是适应性强，缺点是调用次数多、容易重复工具或局部最优。

Plan-and-Execute 先形成可审阅计划，再逐步执行并在必要时重规划，适合多步骤、依赖清楚、成本较高或需要审批的任务。优点是可解释、便于进度展示；缺点是初始计划可能因信息不足而失效。

DevPilot 更接近“计划 + 有界 ReAct”的混合模式：模型提出修改与验证步骤，高风险写回需要审批；每个步骤内部根据工具回执继续决策。简单问答不需要完整计划，代码改动和跨工具任务需要显式计划与验证。

## Q8：Agent Loop 的核心流程是什么？怎样防止死循环？

**核心流程：**

```text
读取当前状态
→ 组装有预算的上下文
→ 调用模型生成结构化决策
→ 校验决策与权限
→ 执行或等待审批
→ 保存观察结果
→ 判断完成、失败、暂停还是继续
```

防死循环不能只靠 `max_turns`。应组合以下机制：

1. 最大轮数、总 Token、总费用、总耗时和单工具调用次数预算。
2. 对“工具名 + 规范化参数 + 关键状态”生成指纹，连续重复且状态不变时终止或换策略。
3. 保存每轮进展信号，例如新证据、文件 Diff、失败类型是否变化；没有进展时触发反思、降级或人工介入。
4. 工具错误分类，参数错误不盲重试，临时网络错误才指数退避。
5. 高风险动作只能在审批范围和次数内执行。

在 DevPilot 中，执行结果必须改变可验证状态；模型反复说“继续尝试”但没有新的 Diff、测试结果或证据，不算进展。

## Q9：LangGraph 中 State、Node、Edge 和 Checkpointer 分别解决什么问题？

**参考回答：**

- State 是一次运行需要共享的结构化状态，例如消息、计划、工具结果、审批状态、错误和预算。
- Node 是对状态进行一次可测试变换的执行单元，例如组装上下文、调用模型、准备工具、执行工具和核验结果。
- Edge 决定节点之间如何流转；条件边根据状态选择继续、审批、失败或结束。
- Checkpointer 保存图执行快照，使进程重启或人工中断后能从可靠位置继续。

在 DevPilot 中，LangGraph 组织上下文、模型、审批、执行和核验；PostgreSQL 检查点保存图状态。但任务、审批、命令、用户消息和审计仍保存为独立业务事实。这样升级框架或排查问题时，不需要把全部业务语义藏在 checkpoint 内部对象中。

## Q10：Agent 的任务状态存在哪里？服务重启后怎样恢复？

**参考回答：**

任务状态需要分层存储：LangGraph checkpoint 记录图执行位置与节点状态；PostgreSQL 业务表记录任务、运行、审批、命令和审计；本地执行器 journal 记录已经开始或完成的真实文件与命令操作；对象存储保存附件和产物。

恢复时不能只读取 checkpoint 然后继续：

1. 重新确认任务是否仍允许运行，登录、租户、项目成员和目录授权是否有效。
2. 读取业务账本，判断上一步是确定未执行、确定完成，还是可能执行但回执丢失。
3. 已完成的纯计算节点可复用输出；有副作用的节点要核验回执或外部状态。
4. 获得新的执行所有权后再推进，避免旧 Worker 和新 Worker 同时运行。
5. 向前端重新发送状态快照，之后继续增量事件。

**项目证据：**DevPilot 使用 PostgreSQL 检查点和任务记录支持中断恢复，并对结果未确认的工具调用保留执行记录，不在恢复时直接重放。

## Q11：有了 Checkpoint，为什么还需要业务表和执行日志？

**参考回答：**

Checkpoint 回答“图运行到哪里、恢复需要哪些状态”；业务表回答“用户提交了什么、谁批准了什么、系统发生过哪些业务事实”；执行日志回答“外部副作用是否真实发生”。三者职责不同。

如果只使用 checkpoint，查询、权限、审计和框架升级都会依赖框架内部序列化格式；更严重的是，数据库 checkpoint 无法证明本机文件、Docker 命令或外部 HTTP 操作是否成功。因此 DevPilot 将图状态、领域事实和设备事实分开保存，再通过 `run_id`、`step_id`、`command_id` 和结果哈希关联。

## Q12：Human in the Loop 怎样落地？用户驳回、超时或服务重启后怎么办？

**参考回答：**

人工审批不是在进程内等待一个 Promise，而是持久业务状态。Agent 产生高风险提案后，保存操作类型、目标、参数、Diff、证据、策略版本和有效期，将运行置为 `waiting_approval` 并释放执行资源。用户批准、驳回或修改后产生新的审批事件，再由 Worker 认领任务继续。

批准后执行前还要重新校验身份、项目授权、文件版本、参数哈希和策略版本，防止“审批时安全、执行时对象已变化”。驳回时记录理由，模型可以在允许范围内重规划；超时则进入过期状态，不能默认批准。服务重启后从业务表和 checkpoint 恢复等待状态，不会因为进程内回调丢失而跳过审批。

DevPilot 将代码修改、测试命令和源项目写回分成不同风险级别，源写回需要独立审批。审批是对固定提案的有限许可，不是永久授权。

# 第三组：工具调用、MCP、Skill 与安全治理

## Q13：模型返回一个 Tool Call 后，后端要经过哪些校验才能执行？

**参考回答：**

我会做五层校验，而不是相信模型给出的 JSON：

1. **协议层**：JSON 能否解析、工具名是否注册、Schema 版本是否匹配、必填字段和数据类型是否正确。
2. **语义层**：路径、日期、金额、枚举和字段组合是否合法；不能只验证字符串类型。
3. **权限层**：当前用户、租户、项目和角色是否有权调用该工具，目标资源是否属于授权范围。
4. **策略层**：是否命中危险操作、是否需要人工审批、单次和累计额度是否超限。
5. **执行层**：生成稳定调用标识和参数指纹，设置超时、输出上限、幂等与审计，再交给隔离执行器。

解析失败时可以把校验错误以结构化形式返回模型，允许有限次数修复；权限不足和高风险拒绝不能通过反复 Prompt 绕过。DevPilot 把目录、命令、登录身份、策略版本和审批绑定到执行请求，本地执行器仍会再次校验，而不是只在模型调用前检查一次。

## Q14：工具超时、返回空、部分成功、脏数据或 500 错误，Agent 分别怎么处理？

**参考回答：**

先统一工具结果协议，例如包含 `status`、`error_type`、`retryable`、`result_ref`、`partial` 和 `external_receipt`，再按失败语义处理：

- **超时**：如果是只读查询，可以按退避策略重试；如果是写操作，超时不代表未执行，应先查询外部状态或进入结果未知。
- **返回空**：区分合法空结果、权限过滤后为空和上游异常；不能把空数组都当失败。
- **部分成功**：保存已经成功的子项和失败清单，后续只补偿或重试安全部分。
- **脏数据**：通过 Schema、范围、单位和业务不变量校验拦截，不能把异常结果继续塞给模型。
- **500 错误**：记录上游错误类别和关联标识；只有明确可恢复的错误才重试，连续失败触发熔断和降级。

重试预算必须受总任务预算约束，使用指数退避和随机抖动，避免多个 Agent 同时打爆下游。超过阈值后转人工或降级到只读模式，并向用户展示真实状态，而不是让模型编一个结果。

## Q15：如何处理重复工具调用和 Agent 死循环？

**参考回答：**

对每次调用生成指纹：`tool_name + canonical_args + resource_version + relevant_state`。如果连续出现相同指纹，且中间没有新的观察或状态变化，就说明模型没有取得进展。此时先返回明确的“重复调用且状态未变化”观察，允许一次改策略；仍重复则停止、降级或请求人工介入。

写工具还需要幂等键，确保相同业务操作不会产生第二次副作用。对于查询工具，可以缓存相同输入的短期结果，减少成本；但缓存键必须包含租户、权限和版本，不能跨用户复用敏感结果。

最大轮数只是最后保险。更可靠的终止条件包括任务完成、不可恢复错误、预算耗尽、用户取消、等待审批、无进展检测和安全策略拒绝。

## Q16：如何设计幂等？工具执行成功但回执丢失时怎么办？

**参考回答：**

请求幂等、流程节点幂等和外部副作用幂等是三层问题。用户提交使用 `request_id` 防止创建重复任务；节点使用 `run_id + step_id + input_version` 复用已完成结果；真实工具使用 `command_id` 与参数指纹绑定，并在执行侧保存 journal。

DevPilot 的处理原则是：执行器先保存本地结果，再上传签名回执。回执丢失时可以重新上传同一结果；如果只知道命令开始过、无法确认是否完成，则标记 `outcome_unknown`，先检查文件、Git 状态或外部系统，不能直接重发。

我不会声称跨模型、数据库、文件系统和外部服务可以做到全局 Exactly Once。实际采用的是至少一次调度、业务幂等、执行回执和未知副作用核验。

## Q16A：用户中途取消任务，或者系统热更新时仍有 Agent 在运行，应该怎么办？

**参考回答：**

取消是持久化业务状态，不等于撤销已经发生的副作用。用户取消后先把任务标记为 `cancelling`，停止创建新步骤，向正在运行的协程或 Worker 发协作式取消；已经发出的模型或外部工具请求可能无法立刻终止，需要等待回执或超时。确认没有在途动作后进入 `cancelled`；结果无法确认的写操作进入 `outcome_unknown`，提示用户核验。

热更新时，一次运行应固定模型、Prompt、工具、策略和图定义版本，老任务按旧版本完成或在安全节点暂停，新任务使用新版本。不能让运行到一半的任务静默切换 Schema。若是紧急安全修复，可以通过全局 Kill Switch 禁用危险工具，并要求受影响任务重新审批或重规划。

## Q17：为什么 Replay 要冻结工具结果，而不是重新调用工具？

**参考回答：**

Replay 的目的通常是复现当时决策，而不是再次改变真实世界。工具结果可能随时间变化，写工具还可能产生二次扣费、二次提交或覆盖文件。如果回放时重新调用，就无法判断差异来自模型、Prompt、检索还是外部数据变化。

因此 Trace 需要保存工具名、规范化参数、调用版本、脱敏结果或不可变结果引用、时间、错误与回执。离线回放时把原结果作为 Observation 注入，只重新执行模型或策略节点。只有在明确的沙箱和固定数据快照中，才允许做“全链路重新执行”，并与普通 Replay 区分。

## Q18：Function Calling 和 MCP 有什么区别？生产级 MCP Server 需要哪些治理？

**参考回答：**

Function Calling 解决模型如何用结构化参数表达调用意图；MCP 解决 AI 应用如何标准化发现并连接工具、资源和提示模板。前者更像模型输出协议，后者更像工具接入协议，两者可以一起使用，并不是替代关系。

生产级 MCP Server 至少需要：身份认证、租户和资源授权、工具级权限、参数 Schema、超时与并发限制、速率和额度控制、审计、敏感信息脱敏、版本兼容、健康检查以及读写能力分级。MCP 只是标准化连接，不能自动保证工具安全。

DevPilot 通过云效 MCP 获取需求与 Bug 工单，也把 MCP 工具放入统一策略体系。模型可以建议调用，但目录、登录身份、策略、审批和结果核验仍由 Harness 控制。

## Q19：工具很多时如何路由？Skill 和 MCP 的边界是什么？为什么要延迟加载？

**参考回答：**

把几十个工具的完整描述一次性塞入 Prompt 会增加 Token、混淆模型选择并放大攻击面。可以先按领域、权限和当前任务过滤，再通过工具目录做粗路由，只加载少量候选工具的详细 Schema。高频核心工具可以直接注册，低频工具按需发现。

Skill 是可复用的任务方法与约束，通常包含目标、步骤、知识、允许工具和验收方式；MCP 是把外部工具和资源接进来的协议。Skill 可以调用一个或多个本地工具或 MCP 工具。Skill 解决“怎样完成一类任务”，MCP 解决“怎样连接能力”。

DevPilot 内置 Figma-to-UI、Bugfix、周报和 Code Review 四类技能。它们不是四个无限自治 Agent，而是四套有明确输入、工具范围和验收条件的任务流程。延迟加载能够减少上下文，并避免给当前任务暴露无关高权限工具。

## Q20：如何设计工具注册中心？选 MCP 还是自研注册中心？

**参考回答：**

工具元数据应包括工具标识、版本、描述、输入输出 Schema、读写级别、资源范围、权限策略、审批策略、超时、重试、幂等支持、并发限制、负责人和健康状态。调用时固定版本，避免运行中工具协议漂移。

如果工具需要跨多个 Agent 客户端复用、生态兼容和动态发现，优先考虑 MCP；如果是内部高频、与业务权限深度绑定、对性能和定制协议要求高，可以保留类型安全的内部调用。实际平台可以同时支持二者，用统一适配层进入同一权限、审计和评测体系。

我的选择依据不是“标准一定比自研好”，而是复用范围、治理要求、迁移成本和团队能力。DevPilot 对外部能力使用 MCP，对本地文件、命令和桌面能力保留受控内部协议。

## Q21：怎样防 Prompt Injection？为什么不能只在 System Prompt 里写“忽略恶意指令”？

**参考回答：**

用户上传文档、网页内容、检索片段和工具返回文本都属于不可信数据。模型无法稳定地区分其中哪些句子是内容、哪些是假指令，所以单靠 Prompt 声明不是安全边界。

工程防线包括：

1. 系统规则、用户请求、检索内容和工具结果分区组装，并给外部内容明确的数据标签。
2. 只向模型提供当前任务必要的工具，工具端再次鉴权和校验参数。
3. 默认只读，高风险写操作需要审批、额度和次数限制。
4. 对输出做敏感信息和目标域检查，限制外部网络与文件范围。
5. 对文档中的注入样本、越权请求和数据外传建立安全回归集。

DevPilot 的真正防线是私有工作副本、目录授权、IPC 白名单、Docker 受限命令、源写回审批和执行侧复核。即使模型被诱导，也不应获得超出当前用户权限的能力。

## Q22：高风险工具如何鉴权、审批、回滚和审计？

**参考回答：**

先把工具按只读、可逆写入、不可逆或外部高风险动作分级。普通用户、内部运营和管理员的可用工具集合不应相同；授权还要绑定租户、资源、金额或范围、时间、次数和策略版本。

审批页面应展示实际动作、目标、关键参数、Diff、依据和潜在影响，而不是只显示“Agent 请求权限”。执行前重新校验授权，执行后保存回执。回滚只能针对确实可补偿的操作；发送消息、扣款或外部提交不一定能真正撤销，不能用“有回滚按钮”掩盖不可逆事实。

审计至少记录用户、租户、任务、模型和 Prompt 版本、工具版本、参数摘要、审批、执行者、结果、错误、时间和关联 Trace。敏感参数可以脱敏或保存哈希，但必须能回答“谁基于什么事实做了什么”。

# 第四组：多 Agent、并发与冲突

## Q23：什么时候应该从单 Agent 拆成多 Agent？Multi-Agent 是噱头还是真解法？

**参考回答：**

多 Agent 只有在以下条件至少满足一项时才有价值：角色需要不同工具或权限；上下文可以明确隔离；子任务能够并行；需要独立验证者降低同源偏差；单个上下文已经过载。否则单 Agent 加工具通常更稳定、更便宜。

拆分应按职责和权限边界，而不是为了模拟组织架构随意起名字。例如 Coding Agent 可以拆成 Planner、Executor 和 Verifier，是因为它们分别负责计划、受控执行和独立验收，并且工具权限不同；不是因为三个模型互相聊天看起来更智能。

DevPilot 采用有界角色和最小交接，不是无限自治 Agent 群。不同角色在独立工作副本中工作，最终改动还要经过真实测试和采用门禁。

## Q24：Planner、Executor、Verifier 和 Supervisor 分别负责什么？

**参考回答：**

- Planner 根据目标和约束拆解任务，输出依赖、验收条件和风险，不直接执行高权限动作。
- Executor 按计划调用允许的工具，输出结构化产物、证据和错误。
- Verifier 使用独立规则、测试或只读工具检查结果，不相信 Executor 的自我声明。
- Supervisor 负责分派、预算、依赖、超时、失败策略和最终汇总，不应把所有原始上下文复制给每个子 Agent。

失败子任务要区分可重试、需要重规划和不可继续。Supervisor 只重试安全且有意义的步骤；部分结果带版本和证据汇总；高风险冲突交给人工。Verifier 最好依赖真实退出码、Diff 和业务断言，而不是再让同一模型简单说“看起来正确”。

## Q25：多 Agent 之间如何通信？共享状态和私有状态怎样划分？

**参考回答：**

Agent 之间不应通过无限自然语言对话传递全部历史，而应通过有版本的任务对象和产物引用交接。共享状态只放任务目标、约束、依赖、已确认事实、产物引用和全局预算；私有状态保存各角色的草稿、局部推理、临时检索和工具细节。

交接协议至少包含 `task_id`、输入版本、输出 Schema、证据引用、完成状态、错误类型和剩余风险。Supervisor 汇总的是结构化结果，不是把所有子 Agent 的长上下文拼接到一起。

这样可以减少信息失真和上下文膨胀，也便于权限隔离。DevPilot 的角色交接强调最小必要信息，源代码或项目资料仍按当前用户和项目权限读取。

## Q26：多个 Agent 读取不同时间的数据，怎样避免状态不一致？

**参考回答：**

任务开始时固定业务快照或记录数据版本，例如仓库 commit、文档版本、规则版本和查询时间。子 Agent 输出必须携带其读取版本。汇总时如果版本不一致，不能静默合并，应重新读取、冲突检测或让上游任务失效重跑。

对数据库记录可以使用乐观锁或版本号；对文件使用内容哈希和 Git 基线；对知识库结果保存文档版本和引用；对外部实时数据明确时效。多 Agent 并行提高吞吐，但不等于可以忽略一致性。

## Q27：多个 Agent 同时修改一个文件或知识库资源，怎样防冲突？需要文件锁吗？

**参考回答：**

优先通过任务分区降低共享写入：给不同 Agent 分配不同模块、文件或私有 Git worktree。最终合并时基于共同基线做三方合并、冲突检测、测试和人工审阅。这比长期持有全局文件锁更适合代码任务。

如果确实需要共享资源，锁粒度应按业务资源而不是整个项目，并设置所有者、租约、超时和 fencing token，防止旧持有者在租约失效后继续写。数据库使用版本字段或条件更新；知识库采用不可变版本和发布流程，而不是多人直接覆盖在线索引。

DevPilot 的实际设计是私有工作副本加源写回审批，减少多个角色直接修改用户项目。不能声称了解 Claude Code 的内部文件锁实现；可以讲自己采用的隔离和合并机制。

# 第五组：上下文工程与分层记忆

## Q28：Harness 中上下文应该怎样分层？System Prompt 里应该写什么？

**参考回答：**

我会把上下文分成六层：稳定系统规则、当前用户目标、结构化任务状态、按需检索证据、工具协议与最近工具回执、对话摘要。System Prompt 只放长期稳定的角色边界、安全原则、输出协议和决策规则，不放会频繁变化的项目资料、全部工具说明和长历史。

组装上下文时为每层设置预算和优先级。当前目标、审批约束和未完成工具调用不能被摘要删除；大段文档只按需检索；历史工具日志保留状态、关键参数、错误和产物引用，不重复放完整输出。每段证据应带来源和版本，避免模型把摘要当成不可质疑事实。

DevPilot 已实现版本化摘要、来源清单和分层记忆，并使用内部保守预算管理上下文；预算是工程口径，不包装成模型官方精确窗口。

## Q29：长上下文如何压缩？滑动窗口和摘要分别适合什么场景？

**参考回答：**

滑动窗口保留最近若干轮原文，适合短期指代和刚发生的工具结果，但会丢掉较早约束。摘要把较早历史压成结构化状态，适合长任务，但存在遗漏和事实漂移。因此生产方案通常组合使用：近期原文 + 结构化摘要 + 可回查原始记录。

摘要不应只是自然语言长段落，最好包含目标、已确认事实、用户约束、完成步骤、未完成事项、错误、产物和来源范围。摘要要有版本、覆盖区间和生成时间；关键审批、禁止动作、外部回执和当前工具协议不能被压缩掉。

若单个受保护内容本身超过窗口，例如超大工具结果或文件，应截断显示、保存完整产物到对象存储，并把摘要和引用放进上下文，而不是悄悄删除尾部。

## Q30：日志预处理怎样减少 Token，又避免关键信息缺失？

**参考回答：**

先做确定性预处理，再考虑模型摘要：去除重复心跳、时间戳噪声和相同堆栈；按错误签名聚类；保留首个异常、根因链、最后状态、关联 ID 和前后窗口；把完整日志保存为产物，只向模型发送索引与关键片段。

过滤规则必须可解释和可回查。若日志中出现此前未见的错误等级、异常类型或关键字，不能因低频被删掉。可用白名单保留 ERROR、WARN、退出码、请求 ID、工具 ID、文件位置和资源指标，并在摘要里记录“省略了多少行、依据什么规则”。

在 Coding Agent 中，真实退出码、测试失败摘要和相关代码位置比完整安装日志更重要；但完整 stdout/stderr 仍应作为证据保存，便于人工展开。

## Q31：短期记忆、用户偏好和长期画像分别存哪里？怎样防止记忆污染？

**参考回答：**

短期任务状态放运行状态和会话数据库；近期对话可以放 Redis 滑动窗口与摘要；用户偏好和长期记忆放受治理的长期存储，例如 Veloxis 使用 Mem0 分层保存用户级和会话级记忆；企业事实应进入业务数据库或知识库，不能只依赖“模型记住了”。

每条长期记忆需要类型、来源、置信度、租户、所有者、创建时间、有效期和可删除性。模型提出的记忆候选不应直接永久写入，高影响偏好需要用户确认。检索记忆时按当前任务、用户与权限过滤，并把“旧偏好”当候选背景而不是强制指令。

例如用户三个月前说偏好保守投资，现在明确要求激进策略，当前明确指令优先；旧记忆应降权、标记冲突或请求确认，而不是偷偷覆盖当前意图。这也是防止记忆污染的核心。

## Q32：并发会话和工具大结果怎样隔离与恢复？

**参考回答：**

会话、任务和工具调用都使用独立标识，缓存键包含租户、用户、会话和版本。后台 Worker 不依赖进程内全局变量保存会话状态，防止多个并发任务串上下文。数据库、向量检索、对象存储和 Trace 也必须携带同样的隔离维度。

工具大结果保存到对象存储或结果表，只把摘要、Schema、关键统计和不可变引用放入上下文。流式传输中为事件分配单调序号；前端断线后携带最后事件序号重连，先获取权威状态快照，再补发后续事件，避免重复和丢失。

# 第六组：RAG、混合检索与回答质量

## Q33：为什么使用 RAG？为什么不把原始文档全部交给 Agent，让它自己检索？

**参考回答：**

全部塞入上下文会遇到窗口、成本、延迟、注意力稀释、权限和版本问题。让 Agent 直接用 `grep` 搜索适合代码仓库中的精确符号和临时探索，但对同义表达、扫描文档、多格式资料和跨用户权限不够稳定。

RAG 把文档解析、切块、索引、权限过滤、召回和引用做成可复用的数据链路，适合大量重复查询。Agent 自主搜索适合开放性、低频、路径不确定的问题。实际可组合：先用索引找到候选，再让 Agent 在授权候选或仓库中做精确读取。

DevPilot 对项目资料使用 ES/Milvus 双路召回并复核版本和权限；代码修复时仍可使用受控文件读取和搜索工具。两者服务不同阶段，不需要二选一。

## Q34：从原始文档到最终答案，完整 RAG 链路是什么？哪些步骤最容易影响效果？

**参考回答：**

```text
文件接入与安全检查
→ 格式解析、OCR/ASR、版面和表格恢复
→ 清洗、结构化与切块
→ 元数据、权限、版本和来源入库
→ 关键词索引与向量索引
→ 查询理解与改写
→ 权限过滤、混合召回、RRF 融合、Reranker 重排
→ 上下文选择与去重
→ 带引用生成
→ 引用校验、拒答与线上评测
```

最容易被低估的是解析和元数据。表格表头丢失、标题层级错误、图片 OCR 失败，会让后面的 Embedding 和重排无法补救。其次是切块和权限：块过小缺上下文，过大稀释主题；如果先召回越权文本再让模型忽略，已经发生泄漏风险。

Veloxis 支持 PDF、Word、TXT、图片、音视频统一解析为 Markdown；图片用 OCR，音频用 ASR，视频使用分片和理解模型。检索层结合关键词、向量、RRF 和 Reranker，最终返回引用。

## Q35：Chunk 应该怎样切？没有标题的 Markdown、利率表和合规文档怎么处理？

**参考回答：**

优先按文档结构和语义单元切，而不是固定字符数。标题、段落、列表、代码块和表格是基本边界；子块继承父标题、文档版本和权限。块不能把定义与例外、表头与数据行、函数签名与实现随意拆开。

没有标题时可根据段落、空行、标点、长度和主题变化生成候选边界，并把文件名或上级目录作为弱标题；必要时让模型辅助生成章节标签，但原始位置和文本必须保留。表格应保存表头、行列坐标、单位和合并单元格关系，并生成适合检索的行级描述；金融利率表或设备参数表不能简单拉平成无结构长文本。

块大小需要用评测集调，不存在统一最佳值。小块精确但上下文不足，大块完整但召回噪声和 Token 成本高。可以使用“小块检索、父块返回”平衡召回与完整性，并用 overlap 只覆盖跨边界的必要内容。

## Q36：短 Query 与长 Query 分别有什么问题？如何做 Query Rewrite？

**参考回答：**

短 Query 信息不足，例如“超时怎么办”，向量可能匹配到多个无关场景；需要结合会话、产品、错误码和当前任务补全，但不能擅自加入用户没说过的事实。长 Query 往往包含多个问题、背景噪声和互相冲突的条件，可以抽取核心意图、实体和约束，拆成多个检索子问题。

Query Rewrite 应保留原查询，并输出结构化结果：主问题、实体、关键词、过滤条件和子问题。检索可以同时使用原查询和改写查询，避免改写错误导致唯一入口丢失。短查询通常提高关键词和上下文权重，长查询做压缩、分解与去重。

不能只比较短 Query 和 Chunk 的字数；Embedding 会把两者投影到同一向量空间，但短 Query 的语义不确定性更高，因此需要上下文补全、关键词召回和后续重排。

## Q37：关键词检索和向量检索各有什么优缺点？RRF 与 Reranker 分别做什么？

**参考回答：**

BM25 关键词检索擅长错误码、型号、函数名、条款号和专有名词，结果可解释，但同义改写能力弱。向量检索擅长语义相似和自然语言改写，但可能忽略精确标识，也受 Embedding 模型和领域差异影响。

两路分别召回后，用 RRF 根据排名而非原始分数融合，避免 BM25 分数和向量相似度尺度不同。RRF 计算思想是对每路排名贡献 `1 / (k + rank)`，简单稳定；Reranker 再对问题与候选文本成对打分，判断更细，但计算成本更高，因此只处理 Top N 候选。

Veloxis 实际采用混合检索、RRF 和 Reranker。DevPilot 当前有 ES/Milvus 与 RRF，但当前事实边界中不声称已经交付独立 Cross-Encoder Reranker。面试时必须区分两个项目。

## Q38：RAG 答非所问时，怎样判断是召回错、重排错、上下文截断，还是模型没用证据？

**参考回答：**

按链路逐层排查，不要直接改 Prompt：

1. 检查解析后的标准答案证据是否存在，版本和权限是否正确。
2. 看关键词与向量各自 Top K 是否召回正确块；都没有是解析、切块、查询或 Embedding 问题。
3. 正确块已召回但融合后丢失，检查 RRF、过滤和去重。
4. 融合候选正确但 Reranker 排后，检查重排模型、输入截断和领域适配。
5. 正确块进入候选但未进入最终 Prompt，检查 Token 预算、父块展开和上下文选择。
6. 正确证据已进入 Prompt 但答案错误，检查提示、模型能力、冲突证据和引用约束。

Trace 必须分别保存每阶段候选和分数，才能归因。只记录最终答案无法知道问题出在哪一层。

## Q39：怎样评估召回质量、排序质量和最终答案质量？如何判断幻觉？

**参考回答：**

检索层使用 Recall@K 衡量前 K 个候选是否覆盖标准证据；排序层使用 MRR 或 nDCG 衡量正确证据是否排在前面；答案层看事实正确性、完整性、引用支持度、拒答合理性和业务任务完成率。

幻觉不能只靠“人觉得不对”。应把答案拆成关键声明，检查每条是否由提供证据或确定性工具结果支持。常见类型包括无证据事实、引用错配、把旧版本当当前版本、错误推导和虚构工具结果。没有足够证据时，正确行为是拒答或请求补充，而不是生成看起来合理的答案。

评测集要覆盖正常、边界、冲突、缺失、越权和提示注入案例。自动指标适合大规模回归，开放式答案仍需要人工抽检；模型裁判只能辅助，不能替代真实引用和业务断言。

## Q40：知识库如何做增量更新、版本管理和权限隔离？

**参考回答：**

文档使用不可变版本和内容哈希。更新时先解析并建立新版本索引，通过校验后切换当前版本；旧任务继续绑定旧快照，避免运行中知识突然变化。删除和撤权需要同时处理全文索引、向量索引、缓存和对象存储引用，并有核验任务确认没有残留。

检索前按租户、项目、角色和版本过滤，返回候选后再回事实库复核 ACL。索引只是候选系统，不能代替最终授权。DevPilot 明确采用“候选索引不代替事实库授权”，Veloxis 也把 RBAC 与文档池过滤联动。

截图中的“五千万向量不停机迁移”没有对应项目事实，面试时可以说明通用思路是双写、回填、影子查询、灰度切读和可回滚，但不要声称实际完成过该规模迁移。

## Q40A：什么时候需要知识图谱或 GraphRAG？它与普通 RAG 怎样配合？

**参考回答：**

普通向量与关键词检索擅长找相关文本，知识图谱擅长显式实体关系、多跳查询和影响分析。例如“某型号设备属于哪个产品线、关联哪些故障和处理规程”需要跨多个实体时，图谱比单段语义相似更稳定。

Veloxis 使用 Neo4j 保存由 LLM 抽取并治理的实体与关系；查询时先从问题抽取实体，执行多跳检索，再把图谱路径与文本 RAG 证据融合进上下文。图谱结果仍要引用原始文档，不能把模型自动抽取的关系当成无来源事实。

并非所有问题都走图谱。简单事实题优先使用低成本混合检索；只有关系明确、多跳价值高的问题才启用图推理。GraphRAG 增加实体消歧、版本、更新和治理成本，必须用评测证明收益。

# 第七组：评测、Trace、坏案例与成本优化

## Q41：Agent 评测体系怎么搭？离线评测、线上观测和人工抽检分别看什么？

**参考回答：**

评测要拆开模型文本质量、工具行为、流程状态和最终业务结果。离线评测用固定输入、环境、权限、工具版本和验收条件做可重复回归；线上观测看真实分布、失败类型、任务成功率、延迟、成本和人工接管；人工抽检处理开放式质量、安全争议和自动指标覆盖不到的场景。

Golden Set（黄金评测集）不只是问题与标准答案。Coding Agent 样本还要包含固定仓库 commit、允许与禁止修改、必须通过的测试、权限和恢复场景。RAG 样本包含标准证据、版本、权限和期望拒答。安全越权属于硬门槛，不能被平均分抵消。

DevPilot 当前有分层工程测试和真实 GLM 场景验收，但不声称已经建立成熟的大规模黄金集平台；Veloxis 使用 LangSmith 调试、LangFuse 线上收集链路，并开展检索效果实验。这两类证据要分开讲。

## Q42：怎样判断 Coding Agent 修复代码真的正确？

**参考回答：**

模型说“已修复”不算正确。我会从六个维度判断：是否满足原始需求；相关测试、类型检查和构建是否通过；是否引入无关 Diff；是否破坏兼容性和安全边界；是否通过真实运行或集成验证；解释是否与实际文件和退出码一致。

评测不能只使用 Agent 自己生成的测试，因为模型可能同时写错实现和断言。应保留独立验收测试、历史回归和禁止动作。不同实现不必与参考补丁逐字相同，只要满足行为约束且没有越权副作用。

DevPilot 保存命令 ID、退出码、stdout、文件 Diff 和结果回执，并区分脚本模型测试与真实 GLM 验收。当前真实编码闭环覆盖提出修改、命令和源同步三类审批，实际 pytest 通过并核对源文件结果；这些指定场景不能换算成通用成功率。

## Q43：Agent Trace 应记录哪些字段？怎样支持 Replay 和坏案例归因？

**参考回答：**

一次 Trace 至少关联：`trace_id`、用户和租户、会话与任务、模型/Prompt/工具版本、输入摘要、上下文来源、检索各阶段候选、模型用量、工具名与参数摘要、权限与审批、状态迁移、结果引用、错误类型、耗时和成本。

不应该无差别记录密钥、完整敏感文档和所有思维过程。必要正文可以保存到受控对象存储，Trace 只保存脱敏摘要和引用。

坏案例归因按“输入—检索—上下文—模型—工具—状态—展示”逐层检查。回放时冻结外部工具结果，比较模型或策略版本；如果需要重新执行全链路，应在独立沙箱和固定快照中完成。修复后的坏案例进入回归集，记录修复层和影响范围，避免只调 Prompt 掩盖解析或权限问题。

## Q44：线上长任务从 5 分钟变成 20 分钟，怎样从入口到出口排查？

**参考回答：**

先按 Trace 分解总耗时：API 排队、Worker 等待、文档解析、检索、模型首 Token/总耗时、工具执行、人工等待、数据库查询和前端订阅。比较 P50/P95、成功与失败样本、不同租户和模型版本，判断是全面退化还是特定步骤。

然后检查队列积压、消费者并发、下游限流、重试放大、数据库慢查询、锁等待、上下文 Token 增长和工具重复调用。一次任务很慢也可能是在等待审批或执行器离线，不能只看 API 健康。

DevPilot 曾定位 RLS 下命令历史查询扫描大量无关记录，通过限定 tenant 与已授权运行范围并增加索引，在合成负载中把相关查询从约 0.6 秒降到约 3 毫秒，同时保留权限和超时回归。这个数字只能说明该查询场景，不说成整个平台 P95。

## Q45：Agent 每天消耗大量 Token，怎样分析和降本？

**参考回答：**

先按任务、模型、步骤统计输入 Token、输出 Token、调用次数、缓存命中、重试、成功率和人工接管，计算“完成一个有效任务”的成本，而不是只看单次价格。常见浪费来自重复发送长历史、工具描述过多、检索片段重复、死循环、失败重试和大模型处理简单任务。

优化顺序可以是：上下文去重与分层摘要；工具和 Skill 延迟加载；检索后只传必要证据；简单分类和改写使用小模型；Embedding、解析产物和确定性工具结果缓存；限制输出和最大步骤；批量处理离线任务；对低风险路径做模型路由。

选择新版本时比较任务成功、安全红线、延迟和单位成功成本。如果满意度几乎不变但成本高 40%，通常优先低成本版本，除非高价值或高风险子集有显著收益；可采用按风险路由，而不是全量使用一种模型。

## Q46：模型供应商降级或模型升级后行为漂移，怎样灰度、回滚和降级？

**参考回答：**

模型、Prompt、工具 Schema、检索和规则都要版本化。升级前跑离线回归和安全集，再做影子请求或小比例灰度，比较任务成功、工具选择、参数错误、延迟和成本。运行开始时固定模型版本，长任务中途不静默换模型。

供应商不可用时按场景降级：只读问答可以切备用模型或返回检索证据；高风险写操作暂停到人工工作台；确定性工作流继续运行；不能为了可用性让弱模型自动执行敏感动作。回滚应恢复完整配置组合，不只是模型名称。

# 第八组：数据层、长任务、消息与并发

## Q47：PostgreSQL、Redis、Elasticsearch、Milvus 和对象存储在 Agent 系统中分别存什么？

**参考回答：**

- PostgreSQL 保存用户、租户、会话、任务、状态、审批、工具调用、规则和审计等强一致业务事实。
- Redis 保存短期缓存、滑动窗口、限流计数、临时通知和短租约，不作为最终事实源。
- Elasticsearch 保存全文倒排索引，擅长关键词、过滤和精确术语检索。
- Milvus 或 PGVector 保存 Embedding 和向量元数据，用于语义召回。
- MinIO 等对象存储保存原始附件、解析产物、大工具结果、报告和不可变快照。

不同存储通过租户、文档、版本和任务 ID 关联。删除、撤权和版本切换必须跨存储同步并核验。DevPilot 主业务使用 PostgreSQL，SQLite 主要用于本地命令日志和兼容路径；Veloxis 使用 PostgreSQL、Redis、Elasticsearch、图数据库和 MinIO 等组件。

## Q48：Redis 在 Agent 场景中除了缓存还能做什么？怎样防缓存击穿、穿透和雪崩？

**参考回答：**

Redis 可以承担短期会话摘要、令牌桶限流、任务通知、临时租约、工具结果短缓存和去重标记。但审批、任务最终状态和审计不应只存 Redis，因为过期或故障会丢失事实。

缓存穿透可用参数校验、空结果短缓存和布隆过滤器；击穿可用单飞请求、互斥重建或逻辑过期；雪崩通过随机过期时间、分批预热、限流和降级缓解。缓存键必须包含租户、权限和版本，避免命中其他用户的数据。删除或更新采用事实库先变更、事件驱动失效，并接受短暂不一致的明确边界。

## Q49：长任务为什么需要消息队列？怎样保证不重复消费和顺序？

**参考回答：**

模型推理、文档解析和图像生成耗时长，不应占住同步 HTTP 请求。API 先持久化任务并返回任务 ID，再投递消息；Worker 消费后推进状态，前端通过 SSE 查询进度。消息队列用于削峰、异步解耦和失败重试，不替代业务状态机。

消息通常只能保证至少一次投递，所以消费者用事件 ID 或任务步骤 ID 幂等处理。需要顺序时按同一任务或资源键分区，并在消费者检查版本；不要追求全局顺序。数据库与消息的一致性可使用事务 Outbox：同一事务写任务和待发布事件，再由发布器发送。

draft.art 的实际证据是 RocketMQ 解耦 Node.js 业务请求与 Python 算法服务，缓冲耗时图像生成任务。截图中的 Kafka 题可以用相同的消息语义回答，但不能声称自己做过 Kafka 生产落地。

## Q50：SSE 流式输出怎样处理断线重连、消息去重和“看到了半句话”？

**参考回答：**

每个事件携带会话、运行和递增事件序号，服务端保存权威消息或事件记录。前端重连时发送最后已确认序号，服务端补发后续事件；若历史已过期，先返回当前完整状态快照，再继续新事件。

模型 Token、工具开始、工具完成、审批等待和最终完成应使用不同事件类型。前端展示中的临时 Token 可以丢弃重建，但已确认消息和工具状态必须来自服务端事实。最终消息要有完成标志和内容哈希，避免断线后重复拼接。

Veloxis 使用 SSE 实现文字流式输出，draft.art 使用 SSE 推送生成状态；语音交互则使用 WebSocket 配合流式 TTS。回答时要区分单向事件流和双向实时音频需求。

## Q51：Python 异步任务如何控制并发、背压、超时和取消？

**参考回答：**

I/O 密集的模型、数据库和对象存储调用使用 `asyncio`；通过 `Semaphore` 或有界 Worker Queue 控制并发，防止同时创建无限 Task。每个外部调用设置连接、读取和总超时；上游队列有容量，满时拒绝、排队或降级，形成背压。

取消不是简单 `task.cancel()` 后不管。协程收到 `CancelledError` 后应释放连接和锁，保存可恢复状态，并继续传播取消；已经发生的外部副作用不能因为本地 Task 取消而自动撤销。CPU 密集解析或本地推理放进进程池或独立服务，阻塞 SDK 可放受控线程池，不能堵塞事件循环。

DevPilot 中 `asyncio` 负责协程并发，LangGraph 负责可恢复流程；两者解决的问题不同。

## Q52：分布式令牌桶和多层限流怎样设计？

**参考回答：**

限流至少分用户、租户、会话、工具和模型供应商五个维度。令牌桶允许一定突发并按速率补充令牌；多实例场景可用 Redis Lua 脚本把读取、补充和扣减放在一次原子操作中。Key 包含限流维度和策略版本，并设置合理过期。

限流不只返回 429。交互请求可以快速失败并给出重试时间；后台任务可以排队；高优先级任务使用独立配额；下游即将过载时减少并发、切小模型或暂停低优先级工具。必须监控拒绝率、排队时间和租户公平性，避免一个大客户耗尽全局容量。

# 第九组：Python 高频基础题

## Q53：Python 装饰器、生成器和上下文管理器分别适合什么场景？

**参考回答：**

装饰器用于不改核心函数代码地增加日志、鉴权、计时、重试等横切能力，使用 `functools.wraps` 保留函数元数据。Agent 工具层可用装饰器统一注册工具、记录 Trace 和校验权限，但业务错误分类不应全部藏在装饰器里。

生成器通过 `yield` 惰性产生数据，适合大文件逐块解析、流式事件和分页结果，优点是节省内存，代价是通常只能顺序消费并需要管理异常和资源生命周期。

上下文管理器通过 `with` 保证文件、数据库事务、锁和临时目录在正常或异常路径下释放。Agent 的执行锁、数据库会话和临时工作副本很适合用上下文管理器表达生命周期。

## Q54：生成器使用 `yield` 后，怎样拿到最终 `return` 的值？

**参考回答：**

生成器执行到 `return value` 时会抛出 `StopIteration(value)`。普通 `for` 循环会吞掉这个异常，因此看不到最终值；可以手动调用 `next()` 并捕获 `StopIteration` 读取 `exc.value`。如果使用 `yield from sub_generator()`，子生成器的返回值会成为 `yield from` 表达式的结果。

实际工程中不建议让普通调用者依赖这个隐蔽返回值。流式处理可以把最终统计作为明确的结束事件，或由封装函数返回结果对象，使协议更清晰。

## Q55：`asyncio` 适合什么场景？它和线程、进程怎样选择？

**参考回答：**

`asyncio` 适合大量 I/O 等待，例如调用模型、HTTP、数据库和对象存储；线程适合无法异步化的阻塞 I/O 库；进程适合 CPU 密集的解析、计算和本地推理。协程不是自动并行，调用 `async def` 只得到 coroutine，需要 `await` 或创建 Task 才执行。

选择原则是先识别瓶颈，再隔离阻塞操作。异步环境里直接调用耗时同步函数会冻结整个事件循环。Agent 长任务通常采用 Web API + 异步客户端 + 消息队列 Worker + 独立 CPU/模型服务的组合，而不是只靠一种并发模型。

更多 Python 题见 [[Python高频面试题与参考答案_JS_TS转Python]]。

# 第十组：团队、需求与生产落地

## Q56：Agent 项目需求很模糊，业务只说“要聪明一点”，怎样拆目标和验收？

**参考回答：**

先把“聪明”转成具体任务、用户和失败成本：用户要解决什么问题、允许使用哪些数据和工具、什么算完成、哪些行为绝对禁止。再选择 20～50 个代表性案例，定义必须满足、允许差异、拒答条件、延迟和成本边界。

版本计划先交付最小闭环，例如“检索到正确资料并给出引用”，再增加工具执行、审批和多 Agent；不要同时追求所有能力。每个迭代用坏案例和线上数据更新评测集，让需求从主观体验逐步转成可验证指标。

## Q57：模型、后端、Prompt、测试和产品之间怎样划责任？谁最容易扯皮？

**参考回答：**

按接口和结果划边界，而不是按技术名词。产品和业务负责目标、风险和验收案例；Agent/Prompt 负责决策协议与上下文；后端负责状态、工具、权限、幂等和可用性；算法或模型团队负责模型服务与能力边界；测试负责评测集、确定性断言和回归门禁。

最容易扯皮的是“答案不好”被笼统归给模型。解决办法是保存分层 Trace：正确证据是否召回、模型是否看到、工具是否成功、最终展示是否完整。接口规范包含 Schema、错误码、版本、超时、幂等和负责人；争议用可复现案例和数据解决。

## Q58：怎样判断一个人真正做过生产 Agent，而不是只跑过 Notebook Demo？

**参考回答：**

看他能否讲清用户和业务量、状态存储、权限、工具失败、幂等、恢复、评测、线上坏案例、成本与取舍。只会讲 Prompt 和框架 API，遇到“工具执行后断网怎么办、用户撤权怎么办、怎样证明任务完成”就无法继续，通常还停留在 Demo。

我的回答会主动区分：Veloxis 和 draft.art 用来证明企业知识库与真实在线链路；DevPilot 用来证明受控 Agent 的工程实现和验证，但当前是预发布受控版本。我不会用几次 GLM 验收冒充长期生产 SLO，也不会把设计方案说成线上事实。

## Q59：团队成员写 Agent 代码不考虑边界和异常，你怎样推动改进？

**参考回答：**

先用真实故障或测试说明风险，而不是只说“代码不规范”。把共同要求沉淀为工具模板、错误类型、超时与重试组件、代码评审清单和回归测试，让正确做法更容易。高风险边界进入合并门禁，例如所有写工具必须声明权限、幂等和审计策略。

沟通时区分认知问题和排期问题：如果成员不知道，就结对设计和复盘；如果时间不够，与产品明确缩小范围，不能默许把异常路径留给线上用户。本人带过 12 人研发团队和 5 人前端资源线，可用招聘、培养、技术评审与跨项目交付的真实案例展开。

## Q60：最近学习的新技术怎样从不了解推进到可上线？

**参考回答：**

先定义要解决的真实问题和现有基线，再阅读官方文档、最小样例和关键源码，做一条包含失败路径的垂直切片。随后补权限、观测、测试和回滚，与现有方案进行质量、性能和维护成本比较，最后小范围灰度，而不是从教程直接全量上线。

DevPilot 从显式异步循环演进到 LangGraph 就能说明这一过程：先验证模型—工具—观察的执行语义，再引入 StateGraph、条件边、中断和 PostgreSQL checkpointer；业务表和执行日志继续保留，避免框架替代业务边界。这个例子比泛泛说“我学习能力强”更可信。
